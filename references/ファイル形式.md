# ファイル形式

## 置き場所

```
loops/
  README.md      このプロジェクトの数字の取り方。★スキルが最初に読む
  index.html     殻。一覧・右ペイン・使い方・ループ表示の枠。生成物。直接編集しない
  L01.html       ループ1つの画面（ループ頁）。生成物。直接編集しない
  L02.html
  rising.css     共通 CSS。assets/ からそのままコピー
  project.css    このプロジェクト独自の CSS（無くてもよい。「合わせて」で上書きされない）
  rising.js      共通 JS。assets/ からそのままコピー
  L01.md         ループ1つ＝1ファイル
  L02.md
  logs/
    L01.md       L01の出来事。必要なときに読む
  .tmp/          更新作業の一時置き場。正ではない
```

**1ループ1ファイル**なのは、1件扱うのに1ファイル読めば済むから。全部を1枚に入れると、1件直すのに全部読むことになる。

## `loops/README.md`

**このスキルがプロジェクト非依存でいられるための鍵。** ここに書いてあるコマンドを読んで実行する。

```markdown
# loops — このプロジェクトの運営ループ

> 現在地と施策評価は `loops/*.md`、出来事は `loops/logs/*.md` が正。`index.html` は生成物なので直接編集しない。
> 運用は `/rising-loop`。

## 数字の取り方

**このプロジェクトで数字をどう取るかを、実行できる形で書く。** rising-loop は毎回ここを読む。
書き方の例:

アクセス解析  <そのまま実行できるコマンド>
              ⚠ 反映の遅れがあるなら、その時間と、直近を見る代わりの方法
DB            <そのまま実行できるコマンド。絞り込み条件も書く>
売上          <台帳の場所と見方>

売上       LINEコンソール（手で入れる）

## 数字を見るときの注意

- staging と本番が同じGA4プロパティにいる。`stage` で必ず絞る
- 〇〇は計測していないので、この数字には出てこない

## 右ペインの相談相手（画面ごと）

ttyd はユーザーのターミナルで立てる（Claude Code の中から起動しない）。

sh <プロジェクトの絶対パス>/loops/chat-pane.sh claude
# codex で使うときは、こちらを代わりに（同じ 7681 番。両方は立てない）
sh <プロジェクトの絶対パス>/loops/chat-pane.sh codex

node_version: 22.18.0

（任意。codex が nodenv 等のシム経由のときだけ要る。`chat-pane.sh` がこの行を読んで
`NODENV_VERSION` を固定する。環境変数 `CHAT_PANE_NODE_VERSION` でも上書きできる）

セッションIDは `loops/.chat-sessions` に自動で溜まる。**手で編集しない。**
仕組みは HTML生成.md
```

⛔ **セッションIDの表は置かない。** IDの正は `loops/.chat-sessions`（`<画面ID> <ai> <ID>` の1行1件）で、
初めてその画面を開いたときに `chat-pane.sh` が作って追記する。
README にも `index.html` にも写しを持たせない（写しがあると必ず食い違う）。

**数字が手入力のプロジェクトなら「手で入れる」と書いておく。** そうすればスキルは聞きに来る。

## ループの md

### frontmatter — 最小限だけ

```yaml
---
id: L01
title: 有料ゲームで遊ばれた回数を、週 20 回に
metric:
  name: 有料ゲームの起動
  start: 0
  now: 0
  target: 20
  unit: 回/週
  measured: 2026-08-29
  window: 過去7日（リリース当日の1日ぶん）
```

動かしているものがあれば、同じ frontmatter に `trials`（配列）を足す。何件でもよい。

```yaml
# --- TRIAL（★進捗バーは出さない。★plan は実現手順のチェックリスト 3〜7項目。全部 ✅ で実施完了。判定日は TRIAL に無い。評価に移してから RECORD に書く）---
trials:
  - id: T02                       # ★拾った順に T01, T02… と振る。RECORD へ移すときも同じ id（画面の record-L01-T02 になる）
    title: ゲームバナーの上にロック解除ボタンを置く
    status: 実現方法を決めるところ
    plan:
      - "✅ 1. 実現方法を決める（案を複数出して選ぶ）→ バナー中央にボタン"
      - "⬜ 2. ボタンを実装する"
      - "⬜ 3. 検証版で確認 → 本番"
  - id: T03
    title: 課金モーダルで有料5本が24時間遊べることを見せる
    status: 全部済み。直しがなければ『完了にして』
    plan:
      - "✅ 1. 文言を決めた"
      - "✅ 2. モーダルに1行足して本番へ（9/15）"
  #=== ★plan はやることを1行ずつ。済んだら ✅、まだなら ⬜（画面も同じ記号）
  #=== ★TRIAL に移した瞬間に全項目を ⬜ で出す。実現方法が未定なら 1 を「実現方法を決める」にする
  #=== ★全部 ✅ になったら status を「全部済み。直しがなければ『完了にして』」にして止まる。RECORD はまだ作らない
```

`metric` には **いつ取った数字か**（`measured`）を必ず付け、取り直すたびに `history` へ1行積む。

```yaml
metric:
  name: 完走率（回数ベース）
  start: 40
  now: 40
  target: 60
  unit: '%'
  measured: 2026-08-30      # ★この数字を取った日
summary: 完走率 40%。1試合 21分半で、途中で抜ける人が7割   # ★一覧の行の一文（.loop-sub）。数字入り・60字以内。更新のたびに書き直す
history:                     # ★上書きしない。取り直すたびに積む
                             #   ただし**同じ日に2回目**のときは、聞かずにその日の点を上書きする
  - at: 2026-08-30
    value: 40
    note: 診断した日（実質2日・559回）
```

**`metric` も `trials` も、無ければ書かない。** `summary` は必ず書く（一覧はこれを写すだけ）。

`loops/.tmp/` は更新作業の一時置き場（数字の生出力・移行前の退避ファイル）。正ではないので、消してよいし、git に入れない。

- 完成型の目標（「LPを刷新する」）は `metric` を省く
- 何も動かしていないループは `trials` を省く

**表示用の状態 enum は追加しない。** TRIAL の実施状況は各 `trials[].status` に書き、画面へ反映する。RECORD の現在評価は本文に根拠・評価日とともに書く。実施完了と評価待ちは両立する。

### 本文 — 散文

```markdown
## レポート

*窓 8/30〜9/1（3日・本番のみ）*

### 数字はここで落ちています

| 開いた | 部屋 | 鍵をタップ | 買った |
|---:|---:|---:|---:|
| 137 | 112 | 32 | 0 |

### 日ごと

| 日 | 8/30 | 8/31 | 9/1 |
|---|---:|---:|---:|
| 買った | 0 | 0 | 0 |
| 折れ線（3日の合計） | — | — | 0 |

## ボトルネック

### 考察

ヘタウマが最後まで遊ばれる → 遊ぶ回数が増える → 有料に手が伸びる。
逆に振れる可能性もあります。無料で満足してしまい、かえって課金しなくなる。

### 施策案

- 有料ゲームを買う前に、遊び方を見せる
- 購入画面のどこで戻ったかを測れるようにする（鍵をタップした32人のうち購入0人）

## 施策の評価

### 購入ボタンを見つけやすくした（2026-09-01 実施）

狙い：購入画面へ進む人を増やす。事前の数値予想は未記録。
変更：ゲーム枠の上に共通の購入ボタンを置いた。詳細は進行ファイルを参照。

| 比較期間 | ホームを見た | 購入画面へ進んだ | 購入 |
|---|---:|---:|---:|
| 実施前 8/25〜8/31（7日） | 100人 | 8人 | 1件 |
| 実施後 9/1〜9/7（7日） | 110人 | 18人 | 1件 |

現在の評価（AI暫定・2026-09-08）：購入画面への誘導は改善傾向。購入増加は確認できていない。
出典：ホーム・購入画面は本番の計測、購入件数は購入台帳。同時期に流入元が変わったため、ボタン単独の効果とは断定できない。
次に見る：同じ流入元で購入画面への到達を比較する。
出来事の詳細：[LOG](logs/L01.md)。
```

上は形式を説明する架空例。実データに写さない。本文の大見出しは **レポート / ボトルネック / 施策の評価**。
GOAL と TRIAL は frontmatter に置く。表の列や小見出しを固定する必要はない。

**RECORD は1施策1項目。** 実施日・見出しを保ち、再計測ではその項目を更新する。必要なら安定したアンカーを付けて LOG から参照する。
過去の施策も要旨と完了日を残す。効果を確かめないと決めたものは A〜E を付けたうえで「効果は測っていない」と本文に書く。決定が分からなければ未記録とする。
**RECORD の項目は「完了にして」で評価に移したときに作る。** TRIAL にある施策の項目を先に作らない（同じ施策が2か所に見える）。

**レポートには「日ごと」の表を置き、そこに「折れ線」の行（または列）を必ず入れる。**
折れ線は「**その日に計測していたらゴールの値がいくつだったか**」で、`loops/index.html` のグラフの線はこの行が元。
窓の規則（累計／3日の平均／7日の平均／累計の割合 など）はループごとに違うので、**行の見出しにその規則を書く**。
窓が揃わない日・集計途中の日・数え方が変わる前の日は `—` にして線を引かない。

⚠️ **この行が無いと、html の `line` は直しようがない**（2026-09-09 に7ループ中2つで線が古いまま止まっていた）。
`history` は計測した日の値しか持たないので、日ごとの線の元にはならない。

レポートは最新の1窓だけ置く。**RECORD の事前値・予想・比較期間・母数・出典は、レポート更新後も残す。**
同じ期間の別の変更や計測方法の変更が評価を左右するなら、その要点も RECORD に置く。

## LOG の形式

`loops/logs/<ID>.md` は出来事の履歴。frontmatter にループの `id` を付けない。

```markdown
# L01 の出来事

- 2026-09-08 ｜評価変更｜購入ボタン：評価待ち → 誘導は改善傾向・購入増加は未確認。根拠は9/1〜9/7の観測。[現在評価](../L01.md)
- 2026-09-01 14:00 ｜本番変更｜ゲーム枠の上に共通の購入ボタンを置いた。[施策](../L01.md)
```

日付順（新しいものを上）で、同日の前後が評価に関係するなら時刻も残す。
普段は前回評価以降の範囲と必要な過去の根拠だけ読む。無変化の再確認・細かい編集・チャットの経過は足さない。
評価の変更履歴は、判断が大きく変わったときの変更前後と理由だけ。ユーザーの確定判定は RECORD に日付付きで保持し、LOG にも残す。

## 評価を更新するとき

同じ施策の観測・現在評価・評価日を更新する。事前予想やユーザーの確定判定を書き換えない。
計測未着なら「評価待ち：実施後の数字が未着。次回は…」と書く。実施完了とは別に扱う。
確定判定後に違う証拠が出たら、確定時の判定を残したまま現在評価に違いを書く。変化を LOG に1件残す。
TRIAL に別の施策が並んでいても、過去施策の評価は更新できる。現在の TRIAL の状態には触れない。

## 旧 RECORD から移行するとき

1. 現在の md・HTML を退避し、既存の編集中の変更を保持する。LOG が既にあれば再移行で重複を作らない。
2. 旧「記録」の原文を `logs/<ID>.md` に移す。古い誤認・判定も移行時に無言で捨てない。今後の追記は LOG の粒度に従う。
3. 旧記録にある実施済みの施策を、施策ごとの RECORD にまとめる。TRIAL にあるものは、ユーザーが「完了にして」と言うまで TRIAL に残す（`SKILL.md`「旧形式の loops/」）。
4. 当時の予想・実施前後の数字・期間・母数・判定日を出典から引き継ぐ。不足は「未記録」。当時の判定者が不明なら「旧記録の判定（判定者未確認）」とし、ユーザー確定と推測しない。
5. 既存の数字だけで読める現在評価を暫定で書き、最後に観測した日を明示する。構造移行のために計測点を増やしたり、欠損値を補作したりしない。
6. 旧記録にしかない、現在の判断を左右する発見は適切なレポートやボトルネックにも要点を残す。単なる発見を施策に仕立てない。
7. HTML の RECORD と LOG 由来の出来事を更新し、実施日・既存判定・数値履歴・TRIAL・画面ID（`PANES`）が失われていないか確認する。

## 新規に `loops/` を作るとき

0. **道具が入っているか調べる。** `command -v ttyd`（1.7 以上）と `command -v claude`。
   **無ければここで止めて、ユーザーに入れてもらう**（macOS は `brew install ttyd`）。
   ★ 右ペインは必須。無い状態で先へ進めない
1. `loops/README.md` を作る（数字の取り方を聞いて書く）
2. 目標を1つ決めて `L01.md` を作る。**最初から複数作らない**
3. 画面を生成する（詳しくは `HTML生成.md`）
   - 殻 `index.html` ← `../assets/index.html`（CONST の `PROJECT_DIR` `SERVICE_NAME` `PANES` と LOOPS の一覧を埋める）
   - ループ頁 `L01.html` ← `../assets/loop.html`
   - 共通 `rising.css` `rising.js` ← `../assets/` からそのままコピー。独自の見た目が要れば `project.css`（無くてもよい）
4. **右ペインを繋ぐ。** やることは2つだけ。
   - `../assets/chat-pane.sh` を `loops/chat-pane.sh` にコピーする（**中身は書き換えない**）
   - 殻 `index.html` の CONST ブロックの `PROJECT_DIR` に、このプロジェクトの絶対パス
     （`loops/` の親）を書く（`#cc-help` の2つのコマンドには `rising.js` がここから埋める）
   ★ **雛形のままにしない**（ttyd は全プロジェクトで1本を共有するので、書き換えないと
   別プロジェクトの cwd で Claude が動き、許可設定が効かない）。
   **セッションは作らない。** 初めてその画面を開いたときに `chat-pane.sh` が作って
   `loops/.chat-sessions` に追記する。詳しくは `HTML生成.md` の
   「右ペインに Claude Code / codex を出す」。

5. **開ける URL を渡して終わる。** `file:///…/loops/index.html` の形（裸のパスはクリックできない）。
   「まずこれを開いてください。次からはこの画面から始めます」と添える

**最初のループは、いま一番気になっている数字で作る。** 網羅しようとしない。増やすのはいつでもできる。
