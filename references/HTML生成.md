## 作るとき

`../assets/template.html` をコピーして、中身を差し替える。**CSS と JS はそのまま使う。**

⚠️ テンプレートの中身は**形式を見せるための架空例**。**構造だけ借りて、文章と数字は必ず置き換える。**

先頭にこれを残す。

```html
<!-- このファイルは loops/*.md と loops/logs/*.md から作られています。
     直接編集しないでください。md を直して、ここを更新します。 -->
```

## 更新するとき

**全文を書き直さない。** 変わったセクションだけ Edit で差し替える。md を直した同じターンで直す。

★ **差し替えたら、タグの開閉が揃っているか数える。見た目では気づけない。**
`</div>` が1つ余ると、そこでセクションの枠が閉じ、後ろのセクションが枠の外にはみ出して**背景色が変わる**。
1つ足りなければ逆に、次のセクションが枠の中に巻き込まれる。

- 差し替えは**要素の開きタグから閉じタグまでを丸ごと**にする。
  「最初に見つかった `</div>` まで」のような検索の境界で切り出して、そこに自分でも閉じタグを書き足すと**二重**になる
- 直したら**同じターンで**下の検算を回し、全画面が揃っているのを見てから返す。ずれが出たら直るまで返さない

```bash
python3 - <<'PY'
import re,io
s=io.open('loops/index.html',encoding='utf-8').read()
for m in re.finditer(r'<section class="screen" id="(s-[^"]+)">', s):
    a=m.start(); b=s.index('</section>', a); sec=s[a:b]   #=== 画面の </section> まで。次の画面までで切ると最後の画面が包み枠を数えて偽のずれが出る
    o=len(re.findall(r'<div\b',sec)); c=sec.count('</div>')
    print(m.group(1), o, c, '' if o==c else '★ ずれ')
PY
```

★ 実際にやった（2026-09-10）。施策案の一覧を5件から4件に詰め直したとき、検索で「最初の `</div>` まで」を切り出し、
そこに自分でも `</div>` を書き足して閉じタグが二重になった。ボトルネックの枠がそこで閉じ、TRIAL 以降がはみ出して背景が変わった。
ユーザーの反応は「**あれ、背景色がおかしくなってるぞ**」「**そういうことがないように skill に明記しろよ**」。

★ **見えるのは html だけ。md は誰も見ない。**
`loops/*.md` を1文字でも直したら、**同じターンで html に反映する。例外なし。**

- ⚠️ **「md が正」は内部の決まりであって、利用者には何の意味も無い。**
  html と md が食い違えば、**利用者は html を信じて判断する。それが正しい。**
- ⚠️ **数字だけでなく文章も。** 表やゲージが合っていても、周りの本文が古ければ
  **古い結論を読ませることになる**
- ★ 直したら、**md の「数字を含む主張」が html に全部出ているか突き合わせる**
- ★ 実際にずれた（2026-09-07）。施策案の人数2か所と、レポート本文2か所が html に無かった。
  さらに **md に「判定しない」と書いてある枠の html に、大きく `E 届かず` が出ていた**。
  利用者は当然 E と読む。**「md には保留と書いてあります」は通らない。**
- ★ **利用者が見ているのは画面だけ。** md に何が書いてあろうと、画面に `E` が出ていれば、それが事実として読まれる。
  **md は AI のための場所ではなく、画面の正本として存在している**（原理1）

★ **1つのループを直したら、必ず一覧（`#s-list`）も見る。同じターンで直す。**
そのループ由来の数字は、詳細画面だけでなく**一覧にも散らばっている**。

| 一覧のどこ | 何が入っているか |
|---|---|
| `.loop-num` | ゲージの値（いま → 目標） |
| `.loop-sub` | 一行説明。**数字が入っていることが多い** |
| `.state` | 施策の件数（実行中 N／評価中 N／施策待ち）。数え方は「一覧のステータス」 |
| `.rev-total` / `.rev-break` / `.rev-note` | **全ループを合算した数字**（累計売上など）と、その「いつ時点か」 |
| `LOOP_HIST` の `days` | **日別の棒グラフ**。⚠️ 数字が JS の配列の中にあるので、文章を直すときに視界に入らない |
| `LOOP_HIST` の `line` | **折れ線**。⚠️ 同上。しかも棒と違って、直し忘れても**線が手前で止まるだけ**なので気づきにくい |

⚠️ **`days` の直し忘れは実際にやった（2026-09-07）。** その日の売上を md の表・ゲージ・
ファネルには入れたのに、棒だけ `0` のままで、画面には**「その日は0円」と表示されていた**。
**md の表と `days` を、日ごとに突き合わせること。**

⚠️ **`line` の直し忘れは7ループ中2つで起きていた（2026-09-09 に発見）。**
原因は「**`line` にあたる行が md に無かった**」こと。`points` の元は `history`、`days` の元は日ごとの表なのに、
`line` だけ元が無いので、md を直しても写しようがなかった。
**いまは各 md の日ごとの表に「折れ線」の行（または列）がある。ここが `line` の正。**
新しいループを作るときも、この行を必ず置くこと。

⚠️ **ゲージだけ直して `.loop-sub` と合算を忘れる。** 実際にやった（2026-09-06）。
**一覧は「全部のループを合わせた現在地」なので、1つ古いと全体が信用できなくなる。**
合算は自分では気づけない（詳細画面を見ても分からない）ので、**直したら一覧を開いて突き合わせる**。

## 画面の構成

```
#s-list         ループ一覧
#s-L01          1つ開いた
```

`id` は `s-` ＋ ループの `id`。ハッシュルーティング（`location.hash`）なので、**ブラウザの戻る／進むが効く**。URLを直に開けばそのループから始まる。

各ループ画面は **GOAL / BOTTLENECK / TRIAL / RECORD** の4セクション。上に `← ループ一覧` を置く。
GOAL の中は上から **数字 → 折れ線 → レポート → LOG由来の出来事の囲み → 一文**。

## ★ 入力は受けない

**HTMLは見る専用。操作はチャット。** HTMLが入力を受けると、正が2つになる。

`file://` で開いた HTML から Claude は呼べない。だから**押せないボタンを置かない**。ボタンは全部、**文言をクリップボードにコピーしてトーストを出す**。ユーザーはそれをチャットに貼る。

### コピーの文言

**先頭にループIDを、続けてループ名を置く。** 貼った文言だけで場所が決まるようにするため。

**形式は YAML ブロック**（`block()` が組み立てる）。貼るだけで、どのループのどこへの話かが決まる。

```
---
loop: L01
section: BOTTLENECK
target: ゲーム枠の上にロック解除ボタンを置く
rule: 必ずスキル rising-loop の手順で直すこと
feedback: |
  ここに入力した本文
---
```

| ボタン | `section` | `target` | 本文のキー |
|---|---|---|---|
| ボトルネックの各行 `指示する` | `BOTTLENECK` | 施策案のテキスト | `feedback` |
| TRIAL の `指示する` | `TRIAL` | 施策名 | `feedback` |
| 各セクションの `コメント` | そのセクション（`GOAL` `REPORT` `BOTTLENECK` `TRIAL` `RECORD`） | 該当項目があれば | `feedback` |
| GOAL の `更新` / 一覧の `全ループ更新` | — | — | `task`（人の言葉ではなく命令なので） |

★ **IDを先頭に置く理由。** 目標のタイトルは運用しているうちに言い換わる（「週20回に」→「週10件に」）が、
**IDは変わらない**。IDがあれば `loops/L01.md` へ直行できる。タイトルだけだと突き合わせが要る。

★ **画面にもIDを出す。** キッカーを `GOAL · L01` の形にする（`<span class="lid">· L01</span>`）。
ボタンを押さずに「**L01の3番やって**」と口で言えるようになる。

★ **番号だけでなく項目のテキストも入れる。** コピーしてから貼るまでの間に項目が片付くと番号が繰り上がる。テキストがあれば取り違えない。

### ファネル（数字はここで落ちています）

**横向きのファネル。高さは値の対数**で、先細りがそのまま落ち方になる（`drawFunnel`）。
帯の中に前の段からの通過率、上下の余白が「ここまでに失った人」。

```html
<div class="funnel-f" data-funnel="L01"></div>
```

```js
var LOOP_FUNNEL = {
  L01: { note: "帯の中の % は…", stages: [
    { name: "起動", value: 593, unit: "人" }, …
  ] }
};
```

- ⚠️ **高さを実数に比例させない。対数にする。** 先頭と末尾で桁が違うのが普通で
  （実例: 593 → 3 で約200倍）、実数だと**末尾が線になって消える**
- ⚠️ **段を横に並べた HTML（`.stage` と矢印を交互に置く形）に戻さない。**
  段が5つを超えると折り返して読めなくなる。実際にそうなって作り直した
- 単位が混ざるときは（人と件など）、`unit` を段ごとに持たせて注記に書く
- **D3 が読めなかったときは、段の名前と数字を文字で出す**（数字だけは必ず残す）

### ボトルネックの行

番号を振り、ホバーで `やる` が出る（タッチ端末では常時表示）。

```html
<div class="open-item active">
  <div class="dot">▶</div><div class="no">1</div>
  <div>ヘタウマの完走率が 29%。1試合に 21分半 かかっています</div>
  <button class="do" data-id="L01" data-loop="…" data-no="1" data-text="…">指示する</button>
</div>
```

`active` と `▶` は **`trial` に載っているものだけ**。他は `·`。

★ **番号があるので、ボタンを押さず「L01の2番やって」と打っても通る。** コピーは手間を減らす補助で、唯一の入口にしない。

### GOAL の履歴（計測日・折れ線・区間の記録）

数字の下に **`<日付> 時点の数字`** を出し、その下に履歴ブロックを置く。

```
8月30日 時点  40%                            診断した日（実質2日・559回）
──────────────────────── 目標 60%
             ●
 この計測までに入ったこと
  8/30  6人以上は26回やって完走ゼロ…
 この計測のあとに入ったこと（次の計測で判定に使う）
  9/1   どこで抜けているかの計測を入れた…
```

- データは `<script>` の `LOOP_HIST` に持つ（数字は `loops/*.md` の `history`、出来事は `loops/logs/<ID>.md` から生成する）
- 折れ線は **D3 で実寸に描く**（`drawChart`）。ファネルと同じ道具に揃えている
- ⚠️ **`viewBox` で横に引き伸ばさない。** 伸ばすと点の丸が楕円に歪み、
  目標のラベルを HTML で重ねる回避策が必要になる。実寸なら `<text>` をそのまま置ける
- ⚠️ **何の線か分からない破線を置かない。** 目標線には必ずラベルを付ける
- ⚠️ 注意書きは `innerHTML` の中に入れる。`insertAdjacentHTML` で足すと**再描画のたびに増える**
- 記録は **「前の計測 〜 この計測」の区間**だけ。最新の点のときだけ、
  **「この計測のあとに入ったこと」**を続けて出す（次の判定で汚染を疑う材料になる）

### ★ 折れ線だけにしない。日ごとの棒を下敷きに敷く

**計測点の折れ線だけだと読めない。** 縦軸が 0〜目標なので、44 → 37 → 37 → 39 のような
実際の動きが潰れて**ただの水平線に見える**。しかも点は数日に1つしか増えないので、
**線が線になるまで何週間もかかる**。

★ **折れ線は数日に1点しか増えないので、それだけでは動きが読めない。** 日ごとの棒を下敷きに敷く。

```
──────────────────────── 目標 60%
   ●─●─●─●─●─●─●─●        ← 折れ線＝その日に計測していたらいくつだったか（line）
  ███ ███ ███ ███ ███ ███   ← 棒＝その日の値（days）
  43% 35% 34% 42% 38% 38%
  8/29 8/30 8/31 9/1 9/2 9/3
```

★ **折れ線は「その日に計測していたらいくつだったか」を日ごとに描く**（`LOOP_HIST` の `line`）。
計測点だけをつなぐと**数日に1点しか増えず、線がほぼ水平のまま**になる。
窓の規則をその日に当てて計算し直せば、**毎日折れる線**になる。

- **単位はゴールの単位のまま。** 棒（その日の実数）とは別の系列なので、桁が違うループは `dualAxis` で軸を分ける
- ⚠️ **日ごとの平均や累計を、棒の値から目分量で作らない。** 窓の規則をその日に当てて計算する
  （例: 過去30日の累計＝その日までの累計／直近3日の平均＝その日を含む3日）
- ⚠️ **数え方が変わった日より前は線を引かない。** 別の指標を1本の線でつなぐと、変化に見えるものが数え方の違いになる
- `line` を持たないループは、これまでどおり計測点をつなぐ（`points` の `end` の位置）
- ★ **計測点を行き来するナビ（前へ／次へ）を付けない。** 使われないうえ、過去の点に戻すために
  レポート・ゲージ・棒の切り方まで分岐が増える。**常に最新だけを出す**
- **棒は直近10本まで。** これをやらないと日が経つほど細くなって、いつか読めなくなる
- ★ **縦軸の上端は `max(目標, 実測)`。** 目標で切ると、目標を超えた日がグラフの外に出て消える
- ★ **ただし目標が実測の5倍を超えるときは、この規則が逆に働く。** 上端が目標になるぶん
  **棒が下に潰れて、日ごとの動きが読めなくなる**。そのときは**縦軸をデータに合わせ**（実測の1.15倍）、
  目標は右上に「**↑ 目標 3,300人/日（グラフの外）**」と文字で出す。
  ⚠️ **破線を上端に引かない。**「上端＝目標」に見えて、距離を読みちがえる。
  どれだけ離れているかは**ゲージ（`value / target`）が持っている**ので、グラフは在りかだけ示せばいい。
  ★ 実際に起きた（2026-09-10）。L05 が「いま283人/日・目標3,300人/日」になった瞬間、
  棒が高さ12%まで潰れて、230〜386人の動きがまったく読めなくなった
- ★ **下げたいループ（コスト・エラー率など）は `targetLabel: "上限"` を置く。** 破線のラベルが
  「目標 0.3円/人」から「**上限** 0.3円/人」に変わる。既定は「目標」なので、上げたいループでは何も書かない。
  あわせて**画面の右の数字ブロックのラベルも「目標」→「上限」**にし、ゲージの下は
  「上限の 91% を使っています」のように**使用率として読ませる**（`value / target` の意味が
  「達成率」から「使用率」に変わるだけで、計算は同じ）
- ★ **棒の数字は棒の内側に深く置く。** 棒と線は近い値を通るので、棒のすぐ上に出すと必ず重なる。
  棒が低すぎて入らないときだけ棒の上に出す
- **日ごとの数字を持たないループは、これまでどおり折れ線だけ**にする。無理に作らない
- データは `LOOP_HIST` の `days`（`[{ d, v }]`）と `dayUnit`（棒の数字に付ける単位。`%` `件` `円`）。
  **正は `loops/*.md` のレポートの日ごとの表**で、`days` はその写し
- ★ **途中の日（今日）も棒に入れる。** `{ d, v, partial: true }` と書くと薄い色になる。**それだけ。**
  「途中」の印・注記・「—」を足さない。毎日見る人には薄いだけで分かる
- データは `line`（`[{ d, v }]`）と `days`（`[{ d, v, partial }]`）。**どちらも正は `loops/*.md` の
  レポートの日ごとの表**。`days` は「その日の値」の行、`line` は「折れ線」の行の写し
- ★ **`line` を html の中で `days` から計算しないこと。** 窓の規則はループごとに違い、
  **棒からは計算できないループがある**（分母が棒に無い／途中で数え方が変わった）。
  ⚠️ 2026-09-09 に「描くときに `days` から計算すれば二重に持たなくて済む」と提案したが、7つのうち3つで成立しなかった。
  **html は表示用。数字の作り方を html に置かない。**
- 各ループの `line:` の上に「★正は loops/LXX.md の◯◯行」とコメントを書く。どこを見ればいいかが分かる
- ⚠️ **数字を更新したら `line` も引き直す。** `days` だけ直して `line` を置き去りにすると、
  棒と線が別々の日を指すことになる
- ⚠️ **線が棒より手前で止まるのが正しいこともある**（窓の外の日・集計途中の日・数え方が変わる前の日）。
  止まっていること自体は誤りの印にならない。**見るのは「いちばん新しい計測点の日が、`line` の最後に入っているか」**
- ⚠️ **`history` の値と `line` の値は、同じ日でも一致しないことがある。これは誤りではない。**
  `history` は**そのとき見えていた値**、`line` は**いまのデータで引き直した値**。
  あとから売れた・外部の集計の反映が遅れて数字が伸びた日はずれる。
  グラフの丸は `line` から打つので画面上は食い違わないが、**md には理由を1行書いておく**

### 更新

**GOAL の見出しに、コメントの左へ置く。** そのループだけ数字を取り直したいときに使う。
**コピー文言は `このループを更新して` の1行だけにする**（一覧の全ループ用は `loops/ の全ループを更新して`）。
★ **手順をここに写さない**（原理1）。`rule:` 行があるので、貼った先は SKILL.md の
「数字を更新し、施策を再評価する」に乗り、数字の取り直しだけでなく**各施策の現在評価の見直し**と
**一覧の合算（累計売上など）**まで実行される。写すと、スキルを直したときにボタン側が古いまま残る。
一覧の上にある `全ループ更新` は全ループ用なので、**役割が違う**（1本だけ見たいときに全部取り直させない）。

### TRIAL

- **進捗バーを出さない。** 判定日は `.trial-status` に文字で書く
- 右に **ステータス**（`.trial-status`）と **`指示する` ボタン**（`.ins`）を置く
- 本文は **要旨**（`.todo` の `ul`・3行まで）。手順の本文は進行ファイルに置き、最後の1行でそのパスを指す。ここは実装の手順書を読む場所ではない（原理6）
- **やることは `<ul class="checks">` に1行1件、頭に `✅`（済）／`⬜`（まだ）を付ける。** md の `plan` の `✅`/`⬜` をそのまま写す

★ **実施が終わっても、TRIAL に「完了」の印を付けない**（原理5）。
  右のステータスに「本番に入れた（9/6）」のような事実だけを書く。ユーザーが「完了にして」と言ったら TRIAL から外し、
  空の TRIAL の表示にする。完了の印は RECORD の `.record-meta` の `実施済`（完了日つき）だけ。

```html
<div class="trial-name">どこで抜けているかを測れるようにする</div>
<div class="head-right"><button class="ins" …>指示する</button><div class="trial-status">本番に入れた（9/1）</div></div>
```

★ **`指示する` があることが TRIAL の役割。** プランを選ぶ・別案を出す・やめる、を全部ここから出す。
**押すたびに実装が走る場所ではない。** 決めるための入口。

```html
<div class="trial">
  <div class="trial-top">
    <div class="trial-name">ゲームバナーの上にロック解除ボタンを置く</div>
    <div class="head-right">
      <button class="ins" data-id="L01" data-loop="…" data-text="…">指示する</button>
      <div class="trial-status">プランを決めるところ</div>
    </div>
  </div>
  <div class="todo">…プラン…</div>
</div>
```

### ★ 塊で見せない（`SKILL.md`「一目で終わりが見えない塊は読まれない」の画面側）

- 各ブロックは **結論1文（`.lede`）＋補足1行（`.sub-lede`）**。それ以上は `<details class="fold">` に畳む
- 数列は `.dtbl`（小さい表）か棒（`.rv-h`）に。文章の中に「／」でつないだ数字を置かない
- 施策案は見出し（動詞で終える）と根拠（`.why`・小さく1行）を分ける
- 太字はブロックに1つ。`<p>` の中に `<details>` を入れない（`<div>` にする）
- 実例：`_design/L01書き直し-index.html` の `#s-L01`

### ★ 薄い補足文を画面に置かない

**仕組みの説明を、薄い小さな文字で画面に添えない。全部ノイズ。**
セクションの下の「この目標で動かすのは1つだけです」「効いた・効かなかったの判定だけでなく…」
「計測が1回だけなので、まだ線になりません」「このファイルは md から作られる生成物です」——
**どれも読む人には要らない。** 仕組みは `SKILL.md` にあれば足りる。

★ **薄い色の補足文字はノイズにしかならない。** 読ませたい文なら濃く書き、読ませないなら置かない。

置いてよいのは**中身のある文**だけ。「場面は1試合につき1回しか数えない」「9月5日ごろに、もう一度見ます」のような、
**数字の読み方や次の予定**は残す。判断は「**これが無いと数字を読み違えるか**」の1問。

### 棒グラフ（日ごと）の単位

**棒は「その日の実額」で描く。** ゴールが月額でも、棒を月換算にしない。
`6470円` のような**実在しない額**が並ぶと、何を見ているのか分からなくなる。

ゴールと単位が違うときは、**目標線と折れ線のほうを1日ぶんに直す**。

```js
dayTarget: 167, dayTargetUnit: "円/日",   //=== 月5,000円 ÷ 30
days: [ { d:"9/4", v:57 } ],              //=== その日の実額
points: [ { value: 1940, dayValue: 64.7, … } ]  //=== 大きい数字は月額、線は1日あたり
```

★ **勝手に換算しない。** 1日ごとの値を見たい場所で月間に直すと、元の数字が読めなくなる。

### レポート（GOAL の中）

`.hist` の中、**折れ線（`.hist-chart`）と記録の囲み（`.hist-recs`）のあいだ**に置く。

```html
<div class="hist-report">
  <div class="hr-title">レポート <span class="hr-when">窓 8/29〜9/3（6日・本番のみ）</span></div>
  <div class="split"> … 既存の2列をそのまま使う … </div>
</div>
```

- **既存の部品を使う。** `.split` / `.split-row`（名前／補足／数字）やファネルの使い回しで足りることが多い。
  ただし**形は目標ごとに違う**ので、列数や表の作りは決め打ちしない。**その数字を読むのに必要な形**にする
- 窓（いつからいつまでの数字か）は `.hr-when` に必ず書く。**これが無いと、いつの数字か分からない**

### グラフ下の出来事は5行まで

`LOOP_HIST` の `recs` / `after` は LOG から生成する出来事の要点。各囲み5行まで。
「前の計測〜この計測」の範囲で、本番変更・外部の出来事・計測の問題など数字を読むのに必要なものを選ぶ。
最新の点だけ、その計測後の出来事を `after` に出す。RECORD の現在評価を過去の区間へ流し込まない。
LOG 全文は HTML に複製しない。必要なときに見に行ける相対リンク `logs/<ID>.md` を置く。

### RECORD — 施策の評価

見出しは **RECORD / 施策の評価**。日付ごとの `.rec-row` の羅列を、施策ごとの `.record-item` に置き換える。
施策名、実施日、現在評価と評価日、比較した数字・期間・母数、判断の限界がひとまとまりで読めるようにする。
**施策の効果と現在の評価がひと目で伝わるようにする。** 重要な数字は強調し、単位・期間・比較対象も近くに示す。
経緯や関係性は、図や時系列にすると理解しやすい場合に視覚化する。補足は必要に応じて折りたたむ。
強調した観測値がそのまま施策の効果だと誤解されないよう、効果が未確認ならその評価も数字の近くに見えるようにする。判断に必要な限界は折りたたみの中だけに隠さない。
レイアウトや図の種類は固定せず、内容に合わせて選ぶ。テンプレートは参考例であり、同じ配置や必須フィールドの羅列に当てはめない。

- 現在の評価を先に読めるようにし、根拠を続ける。**評価の文（`.rvd-body`）は 120 字以下**、それ以上は本文へ。評価待ちは理由を添える。
- 「測らない」を段階の位置に出さない。計測を入れる施策は計測が走れば A。売上への効果は本文に「測っていない」と書く
- AI の暫定評価とユーザー確定判定を区別する。確定判定は判定日とともに残し、現在評価と違っても消さない。
- 実施した施策には `実施済` と完了日を残す。効果測定しない決定や、方針未記録も本文で読めるようにする。
- 施策ごとのコメントはループID・施策名を含めてコピーする。コピーからチャットに貼る仕組みは共通モーダルを使う。
- **各項目の評価日を常に表示する。** いつ時点の評価かが分からないと、根拠と評価がずれて読まれる。
- 評価を更新しても施策は同じ項目。履歴の羅列を増やさない。判断の大きな変更だけ LOG へ残す。
- 空なら「まだ実施済みの施策はありません」。外の出来事や気づきで埋めない。

### セクションの見出し

**セクションの上端に4pxの色線をセクション幅いっぱいに引き、その線の直下・左端に台形のタブを置く。**
タブには**英字と日本語の両方**を入れ、これが見出しを兼ねる（下に大きな見出しを重ねて置かない）。

| | GOAL | BOTTLENECK | TRIAL | RECORD | 一覧 |
|---|---|---|---|---|---|
| 線 | `#3f5a72` | `#9b6518` | `#52751f` | `#46534b` | `#74827a` |
| タブの地 | `#eaeff4` | `#f7efe2` | `#eef4e4` | `#eef1ec` | `#eef1ec` |
| 文字 | `#33495c` | `#7d5214` | `#3f5c17` | `#2c3a32` | `#3f4b44` |

- 台形は `clip-path`。⚠️ **`clip-path` と `filter` を同じ要素に置くと影が切られて消える**ので、形は `::before`、影は本体に分ける

### 施策案の行

**左に `💡施策 N` の緑ピル**（地 `--good`・枠 `#54604d`・白抜き・幅96px）。番号は残す。

### 出来事のLOG

**`<details>` のトグルで開き、中身は `<iframe src="logs/L01.md">` で読む。**
⚠️ **`fetch` は使えない。** `file://` で開いたページからの `fetch` は CORS で弾かれる（オリジンが `null`）。
iframe なら通り、`.md` はブラウザがそのままテキストで出す（＝装飾なし）。ダウンロードにもならない。

**「変更」「次に見る」は操作する側の材料**で、画面を見る人は使わない。md にあれば足りる。
折りたたみに入れて画面へ持ち込まない。

★ **ただし「事前の予想」と「判定日」は画面に出す。**
判定の場で予想が手元に無いと、**後から数字を見て「効いた」と言えてしまう**。
評価カードのすぐ下に1行で出し、**無いときは「予想 未記録」と書く**（無いことも判定の材料なので隠さない）。
効果測定しないと決めた施策は、その決定を書く。

```html
<p class="record-forecast"><span>予想</span>2週間で 7件 → 10件<em>判定 9/16</em></p>
<p class="record-forecast none"><span>予想</span>未記録</p>
```

### 評価の見せ方

**`A / B / C / D / E / -` の5段階を、濃い地に白抜きで左に置く。**
段階の下に意味を1語（狙いどおり／おおむね／半分／わずか／届かず／未評価）添え、**凡例を別に置かない**。

| | A | B | C | D | E | - |
|---|---|---|---|---|---|---|
| 地 | `#4a6b1c` | `#6b8536` | `#9b6518` | `#a9522c` | `#a8443a` | `#e6eae2` |
| 字 | 白 | 白 | 白 | 白 | 白 | `--dim` |

**A（緑）から E（赤）へ寄せ、明るさは揃える。** 1つだけ目立つ色にしない。
**`-`（未評価）だけ薄い地に濃い字**にして、まだ評価が付いていないことを色で分ける。

- ⚠️ **点数（n/10）にしない。** 細かい点差に意味を持たせられず、分母の説明も要る
- ⚠️ **A〜E は薄くしない。** 薄いと、そもそも目に入らない
- ⚠️ **右上にステータスピルを置かない。** `実施済` `効果測定しない` は実施日の行（`.record-meta`）に書く
- ★ **評価は薄いと目に入らない。** 濃い地に白抜きで置く。**記号ひとつでは意味が伝わらない**ので、必ず言葉（狙いどおり／半分…）を添える。

### 図は CSS の棒だけで描く

**JS も D3 も使わない。** 幅が変わっても崩れず、`LOOP_REDRAWS` への配線が要らない。
縦棒（日ごとの推移＋実施日の印）と横棒（前後・内訳の対比）の2つで足りることが多い。

- **実施日の棒に印を付ける**（`.rv-col.on`＋ラベルを `--warn`）。前後がその場で読める
- **数え方が変わった区間・条件が違う区間は斜線**（`.rv-col.alt`）にして、同じ色で並べない
- 図の下に1〜2行で、**実施前 → 実施後**を単位つきで書く
- ⚠️ **強調した数字がそのまま効果に見えないよう、限界を図のすぐ下に出す。** 折りたたみに入れない

ラベルは既存の `.rec-v` のピルを使う。評価待ちや不明は `warn`、明示的な改善の評価は `good`、悪化は `bad`。
色は表示上の補助で、状態 enum として md に保存しない。実施確認・効果測定しない施策は `todo` を使う。
グラフを持たないループでも、施策の評価日と実施日は表示する。

## 右ペインに Claude Code / codex を出す

★ **これは画面の中核。作るときに必ず入れる。**
画面のボタンはすべて「文言をコピーする」だけの作りなので、**貼る先がその場に無いと往復が成立しない**。
ペインを省くと、コピーするたびに別ウィンドウへ切り替えることになり、この画面を見る意味が薄くなる。

**作りはじめる前に、入っているかを必ず調べる。**

```bash
command -v ttyd && ttyd --version              #=== 1.7 以上
command -v claude || ls ~/.local/bin/claude
command -v codex                              #=== codex で使うなら（任意。無くても止めない）
```

無ければ**そこで止めて、ユーザーに入れてもらう**（macOS は `brew install ttyd`）。**勝手に入れない。**

⚠️ 実装は `ttyd` に依存する。**入らない環境でだけ省く**。
省いたときは、その旨を `loops/README.md` に1行書いて、次に作る人が「入れ忘れた」と誤解しないようにする。

画面の右に **Claude Code のターミナル**を 360px で常駐させる。コピーした文言を、
別ウィンドウへ切り替えずにその場で貼れる。

**セッションIDは HTML に持たせない。** 右ペインは、プロジェクト専用のランチャー
`loops/chat-pane.sh` 経由で ttyd を立てる。**このファイルはスキルの `assets/chat-pane.sh` を
そのままコピーして置くだけで、中身は書き換えない。**

**先にこれを1本立てておく**（立っていない間はペインが黒いだけ）。`ttyd` は `brew install ttyd`（1.7 以上）。
コマンドは2種類。**どちらを立てるかで、右ペインの道具が決まる。画面側に切替は無い。**

```bash
#=== Claude Code を相談相手にするとき
sh <プロジェクトの絶対パス>/loops/chat-pane.sh claude

#=== codex を相談相手にするとき（同じ 7681 番。★両方は立てない）
sh <プロジェクトの絶対パス>/loops/chat-pane.sh codex
```

ランチャーがやること（起動モード）:

- `cd` する**前に** `ttyd` と指定した AI の実体を `command -v` で解決する。
  無ければ **ttyd を立てずに**「何が無いか」を1行出して終わる（黒い画面で悩まなくて済む）
- codex が nodenv 等のシム経由のときは `NODENV_VERSION` を固定する。版は
  `loops/README.md` の **`node_version:` 行**（無ければ環境変数 `CHAT_PANE_NODE_VERSION`）から読む。
  ⚠️ 固定しないと `cd` 先の `.node-version` に引きずられて `command not found`（exit 127）になり、
  ttyd が即死プロセスを繋ぎ直し続けてペインがちらつく
- 7681 番が既に使われていたら、その旨を出して終わる（**勝手に kill しない**）
- `ttyd -W -a -p 7681 -s 9 sh <自分自身> --open <ai>` を exec する

⚠️ **同じ 7681 番なので、立てられるのはどちらか一方。** 立て替えるときは先のほうを止める。
道具を変えるのに画面（HTML）を触る必要は無い。**立てたコマンドがそのまま右ペインの道具になる。**

⚠️ **ttyd は自分のターミナルで起動する。AI は起動しない**（Claude Code の中から起動すると、右ペインの会話が保存されなくなる）

`-a` は URL から引数を渡すフラグ。`?arg=<プロジェクトの絶対パス>&arg=<画面ID>` が
`--open <ai>` の後ろに続く位置引数として渡るので、ランチャーは `--open <ai> <パス> <画面ID>` を受け取る。
画面側は `<iframe src="http://localhost:7681/?arg=…&arg=…">` を直接指すだけで、
**プロキシもローカルサーバも tmux も要らない。**

★ **画面から渡すのは2つだけ**（パスと画面ID）。**渡す側は道具もセッションIDも知らない**というのがこの形の要点。

⚠️ **`PROJECT_DIR` を省かない。ttyd は1本を全プロジェクトで共有する。**
`claude --resume` の cwd は**ttyd を起動した場所**になるので、渡さないと
**最後に ttyd を立てたプロジェクトの cwd が、全部の右ペインに適用される**。
画面から自分のプロジェクトの絶対パスを渡し、ランチャーがそこへ `cd` してから resume する。
これを忘れると**別プロジェクトの許可設定・環境で動く**。★実際に起きた（2026-09-10）。
watcher の右ペインが `liny_ai_lab_proj` の cwd で動き、watcher の許可設定が効かなかった。
- `index.html` の `var PROJECT_DIR` に **`loops/` の親の絶対パス**を書く。
  ★ **雛形のまま置かない**（テンプレートは `'/絶対パス/プロジェクト'` というプレースホルダ）
- ★ `encodeURIComponent(PROJECT_DIR)` は必須。**`+` はクエリ文字列で空白に化ける**ので `%2B` にして渡す
  （`+Works` `+watcher_proj` のようなパスがそのままだと ` Works` になって `cd` が失敗する）

`file://` で開いた HTML からでも映る（ttyd は `X-Frame-Options` を出さない。1.7.7 + Chrome で実測済み）。
★ ここが成否の分かれ目なので、移植したらまず**プロンプトが出るか**だけ先に見る。

⛔ **`-s 9` を外さない。`claude` は SIGHUP も SIGTERM も無視する。**
ttyd の既定は SIGHUP、`-s 15` でも死なない。切断されても `claude` が残り続け、
**タブを開くたびに1個ずつ増えて溜まる**（実測: 21時間で58個。同じセッションIDを24プロセスが
同時に開いていて、履歴ファイルへの書き込みがぶつかる状態だった）。SIGKILL だけが確実に効く。
- 溜まっているかの判定は接続数とプロセス数の比較。**一致していれば漏れていない**
  ```bash
  T=$(pgrep -x ttyd); echo "接続 $(lsof -nP -p $T -a -i TCP | grep -c ESTABLISHED) / プロセス $(pgrep -P $T | wc -l)"
  ```
- ⚠️ 接続が残っているのに「タブは閉じた」と食い違うときは、**Playwright の常駐検証ブラウザ**
  （`Google Chrome for Testing`）が掴んでいることがある。普段の Chrome だけ見て判断しない

⛔ **tmux / screen を噛ませない。** プロセスが残る問題は上の `-s 9` で解決する。
tmux を挟むと**ホイールでスクロールできなくなる**（tmux が画面を描き直すので xterm.js 側に
スクロールバックが溜まらない）。macOS 同梱の `screen` は 4.00.03（2006年）で truecolor を
解釈できず、**全文字が「背景グレー＋文字サーモン」に化ける**。どちらも実測で踏んでいる。

### 画面ごとに同じ相手へ戻す

画面（`#s-L01` など）と相手の対応は **ランチャーが持つ**。HTML は**画面IDの一覧だけ**を持つ。

```js
//=== 画面IDの一覧。セッションIDはここに持たない
var PANES = ['s-list','s-L01','s-L02'];
//=== 渡すのは2つだけ: プロジェクトのパス / 画面ID
f.src = BASE + id;
```

**セッションIDは `loops/.chat-sessions` が正。**`<画面ID> <ai> <セッションID>` のスペース区切りで1行1件。
`index.html` にも `README.md` にも写しを置かない（写しがあると必ず食い違う）。

⛔ **`iframe.src` を書き換えて切り替えない。** 書き換えると接続が切れ、戻ってくるたびに
`claude --resume` が最初から立ち上がって**入力できるまで10秒待たされる**。
**画面ごとに iframe を1枚ずつ作って重ね置きし、表示だけ切り替える**（`sync()` の `frames` を見る）。
一度作った iframe は捨てない。2回目以降の切り替えは瞬時になる。
- 非表示は `visibility:hidden`。**`display:none` にしない**（幅が0になり、戻したとき
  xterm が組み直して一瞬崩れる）
- 引き換えに、**開いた画面の数だけ `claude` が同時に常駐する**（7画面なら7個）。
  行き来した回数では増えないので溜まりはしないが、メモリはそのぶん食う

### セッションは初回接続時にランチャーが作る

`--open` モードは、ブラウザが**その画面を初めて開いたとき**にこう動く。

1. `cd <プロジェクトパス>` する
2. `loops/.chat-sessions` から `<画面ID> <ai>` の行を探す
3. **無ければその場で作る**
   - claude: `uuidgen` でIDを決めて `claude --session-id <U> -p '<窓口プロンプト>'`。
     ★ `~/.claude/projects/*/<U>.jsonl` **があるかを確かめてから**採用する
     （セッションが無くてもペインは黒くなるだけで、画面からは失敗と区別がつかない）
   - codex: IDは自分で決められないので `codex exec --json --skip-git-repo-check '<窓口プロンプト>' </dev/null`
     の出力から `thread.started` の `thread_id` を拾う。
     `</dev/null` が無いと標準入力を待って止まることがある
   - 窓口プロンプトは
     `これは <プロジェクト名> の loops/index.html 右ペイン（<画面ID>）専用の窓口です。返事は「了解」だけ。`
     （画面IDが `s-list` 以外なら `loops/<ID>.md` の `title:` を読んで `（L01「…」）` を添える）
4. できたIDを `loops/.chat-sessions` に1行追記する
5. `claude --resume <ID>` / `codex resume <ID>` を exec する

⛔ **作成に失敗しても、即終了しない。** エラーを出して `exec tail -f /dev/null` で止める。
ttyd は子が死ぬと繋ぎ直すので、**即死すると「即死→再接続→即死」の無限ループ**になる。
★ 実際に起きた（2026-09-14。codex のIDが空のまま渡り、`codex resume ""` がループした）。
**「codex を使わないなら空でよい」という規約を捨てて、この形にしたのがそもそもの理由。**

⛔ **`--open` の中では `CLAUDECODE` `CLAUDE_CODE_CHILD_SESSION` `CLAUDE_CODE_SESSION_ID` `CLAUDE_PID`
を `unset` してから exec する。** ttyd の起動元が Claude Code の Bash だった場合、
これらが子に降りてきて**対話モードの claude が会話を保存しなくなる**。

- 1本あたり10秒ほど。初めて開く画面でだけ待たされる（2回目以降は resume だけ）
- ⚠️ **`.chat-sessions` は手で編集しない。** ランチャーが追記する

- ⚠️ **画面を切り替えると、それまでの claude は終わる**（次に開くと続きから）。走らせている最中に切り替えない
- ⚠️ 同じ画面を2つのタブで開くと、2つ目が `already in use` で弾かれる
- ペイン上端のバーは `💡 15秒たってもチャットが出ない？` ボタン1つ。押すと `#cc-help` が開く
  （起動を忘れたときの受け皿）。中身は4つだけ＝**仕組み**（ターミナルで動いている
  Claude Code／codex を映しているだけ・動いていないと真っ黒）→ **①コマンド2本**
  （`sh <PROJECT_DIR>/loops/chat-pane.sh claude` と `… codex`。どちらも `data-copy` でクリックコピー。
  ★ `data-copy` と `<code>` の**両方**にプロジェクトの絶対パスを埋める）→
  **②リロード** → **15秒ほどかかることがある**。⚠️ 説明を足して長くしない
- ⚠️ **ダイアログは `z-index:97`**（ペイン90・トグル95 より上）。トースト(96)はその下になるので、
  コマンドを押したら**先にダイアログを閉じてから**コピーさせる（閉じないとトーストが見えない）
- ⚠️ **Claude と codex でIDは共用できない。** `.chat-sessions` は `<画面ID> <ai> <ID>` の3列なので、
  同じ画面でも AI ごとに別の行になる。**道具の切替は chat-pane.sh をどちらで立てたかだけで決まる**
- ★ **貼り先の案内を出し分ける。** 他のボタンは「AIに貼って伝えてください。」でよいが、
  このコマンドだけは**ターミナル**に貼る。`showToast(text, ok, foot)` の第3引数を足し、
  ボタン側に `data-foot="ターミナルに貼って実行してください。"` を持たせて渡す
  （`copyText` → `legacyCopy` → `showToast` の3つに引数を通す）。**ここを写し忘れると案内が嘘になる**
- **右上**のトグルで開閉。状態は `localStorage` の `cc-pane`。既定は開く（右下はトーストとぶつかる）
- ★ **トグルの見た目はここが正。プロジェクト側で変えない。**
  ```css
  #cc-toggle{ padding:3px 7px; border-radius:5px; font:700 12px/1.4 …; background:var(--good); color:#fff }
  ```
  文言は `AI ◂` / `AI ▸` の2つだけ。**▸◂ は「押すとどちらへ動くか」**を指す（開いている＝`▸`＝閉じる方向）。
  ⚠️ **`template.html` の値を、その画面の古い値で上書きしない。** 直すときは
  **テンプレートを直してから画面へ写す**（逆をやると、あとから全プロジェクトへ配られる値が壊れる）。
  ★ 実際にやった（2026-09-10）。テンプレートを 12px に上げてあったのに、画面側の 10px を正だと思って
  **テンプレートごと 9px に下げた**。「反映されていない」という指摘を「もっと小さく」と読み違えたのが発端
- 閉じている間は繋ぎに行かない（`sync()` が即 return し、iframe をまだ作らない）
- `body.pane-on` に `padding-right` を足して本文を避ける（`--pane: 360px`）
- ⚠️ **右下に固定しているもの（トースト・トグル）は `body.pane-on` で `right` をペインぶん寄せる。**
  `z-index` も上げないとペインの下に潜る（トーストは 9 のままだと隠れる）
- ⚠️ **コマンドを `…` で丸めない。横スクロールにもしない。折り返して全文を見せる**（`white-space:pre-wrap; overflow-wrap:anywhere`）。丸めると中身が見えず貼るのが怖く、横スクロールは読みにくい


★ **入力は受けないまま。** `file://` と `http://localhost:7681` は別の出どころなので、
画面のボタンから iframe の中へ文字列を送ることはできない。**ボタンは全部コピー動作のまま**で、
ユーザーが右のペインに貼る。送信までやるにはローカルサーバを立てて同じ出どころに揃える必要があり、
そのとき「HTMLは見る専用」が崩れる。**いまは崩さない。**

⚠️ `ttyd` に `--base-path` を付けない。プロキシ越しに応答が壊れる（1.7.7 の既知の不具合）。
いまはプロキシが無いので関係ないが、将来挟むときに踏む。

## ★ 実寸で描く図は、描き直しをつながないと壊れる

折れ線もファネルも **`clientWidth` を見て実寸で描く**。つまり**幅が変わったら描き直す必要がある**。
描き直しは `window.LOOP_REDRAWS` に関数を積んでおき、次の3つから呼ぶ。

| きっかけ | なぜ必要か |
|---|---|
| `show()`（画面の切り替え） | **隠れている画面は幅が0**。初回の描画では何も描けていない |
| `resize` | 窓の大きさが変わる。連続で来るので間引く |
| 右ペインの開閉（`set()`） | ⚠️ **`padding-right` が変わるだけで `resize` が飛ばない。** 忘れると古い幅のまま残る |

★ 実際に踏んだ: ペインの開閉だけつなぎ忘れ、**枠474pxにSVG794px**がはみ出したまま気付かなかった。

## ★ 見た目を規約で縛らない

**決めるのは「何を置く場所か」だけ。** 列の数・行数・表の形は、**目標ごとに変わる**。
数字の組み合わせも見せ方も、ループによって違うのが当たり前で、そこを規約で固定すると
**その数字を読むのに必要な形が作れなくなる**。

★ **レイアウトまで決め切らない。** 目標によって数字の組み合わせも表記も違うので、
細かく指示するほど、その目標に合わない形を強いることになる。

規約に書くのは、**役割**（どこに何を置くか）と、**壊れるとまずいこと**（点と連動して畳む、窓を書く）だけ。

## デザイン

テンプレートの CSS をそのまま使う。**新しい色や角丸を足さない。**

```
--shell:#f0f2ed   ページ地
--surface:#fffefb  カード地
--line:#cbd2cb     枠線
--ink:#1c2821      本文
--sub:#536159      補足
--dim:#87918b      薄い
--accent:#ccef67   主ボタン
--good:#52751f  --warn:#9b6518  --bad:#b95448
```

- 幅 `max-width: 880px`
- 枠は **1px フラット**。影は使わない（トーストとモーダルだけ例外）
- セクションは横罫で区切る。箱で囲まない
- キッカー（`GOAL` `BOTTLENECK`）は `ui-monospace` ＋ `letter-spacing:.12em`
- 数字も `ui-monospace`。**桁が揃わないと比較できない**
- 進捗バーは `.progress-track` / `.progress-fill`（`width:%` で指定）

### 一覧のステータス

**ループ一覧の各行の右。状態の名前ではなく、施策の「件数」を出す。**

| 出るもの | 数えるもの | 色 |
|---|---|---|
| `施策待ち` | どちらも0件のとき | グレーの輪郭だけ |
| `1 実行中` | **TRIAL にあるもの** | 緑の点 |
| `2 評価中` | **RECORD にあって、TRIAL に残っていないもの** | 琥珀の点 |

★ **評価中は「RECORD の全件」ではない。** 本番に入れた施策は TRIAL に残ったまま RECORD にも作られる（`SKILL.md` の2段階）ので、
全件を数えると**同じ施策が実行中と評価中の両方で数えられる**。TRIAL に残っているものは実行中だけに数える。

★ **状態の名前（`試行中` `承認まち` `未着手` のような enum）を作らない**（原理6）。数えた結果だけを出す。
プランを決めている途中のものも TRIAL にあるので `実行中` に含まれる。**どこまで進んだかは、ループを開いて `.trial-status` を読む。**

```html
<!-- 0件 -->
<div class="state"><div class="st idle"><span class="st-dot"></span>施策待ち</div></div>

<!-- TRIAL 1件 ＋ 観察中 2件 -->
<div class="state">
  <div class="st run"><span class="st-dot"></span><span class="st-n">1</span><span class="st-lb">実行中</span></div>
  <div class="st rev"><span class="st-dot"></span><span class="st-n">2</span><span class="st-lb">評価中</span></div>
</div>
```

- **色は8pxの点だけに持たせる。** 枠や塗りを足すと、行の罫線やゲージと競って一覧が騒がしくなる
- **数字は 17px の等幅**（ラベルは 11px）。遠目には数字だけが読めればいい
- ステータス列の幅は **100px**。ラベルを増やして幅を広げない

## 空のとき

ループが空でも寂しくしない。**何を待っているかを書く。**

```html
<p class="forecast">
  リリースが <strong>8月29日</strong> なので、翌日戻ってきたかどうかを見るには、あと数日かかります。
```

TRIAL が空なら破線の枠（`.trial.empty`）にして、提案があれば出す。

## 確認

作ったら `file://` で開いてもらう。見てほしいのは3つ。

1. 一覧 → ループ を**クリックで往復できるか**
2. ブラウザの**戻るボタンが効くか**
3. `指示する` と `コメント` と `更新` で**コピーが通るか**（`navigator.clipboard` が拒否された場合は `execCommand` に落ちて、文言を9秒出したままにする）
4. **セクションの背景が途中で変わっていないか。** 変わっていたらタグの開閉がずれている（「更新するとき」の検算を回す）
5. 右ペインの下に **"Transcript saving is off"** が出ていないこと（出ていたら ttyd の起動元が Claude Code の中）
6. **codex で立てたときも**、右ペインに「了解」の会話が見えること
   （見えないなら `loops/.chat-sessions` に codex の行ができているかを見る。
   作成に失敗していると、ランチャーがエラーを出したまま止まっているはず）
7. `loops/chat-pane.sh` が置いてあり、`index.html` に `SESS` が残っていないこと

RECORD 更新後は、同じ施策が重複しないこと、評価日と根拠が読めること、過去の計測点で現在評価の注意が出ることも確認する。
